## 1. 배경 및 현황

우리 팀은 편리한 요청 정보 및 인증 사용자 관리를 위해 전역 상태 객체인 `Rq`를 사용하고 있습니다. 초기 설계 당시, 로그인한 사용자의 엔티티를 쉽게 가져오기 위해 다음과 같은 코드가 작성되어 있었습니다.

```kotlin
@Component
class Rq(private val userService: UserService) {
    // 현재 로그인한 사용자의 Entity를 반환
    val member: User?
        get() = userService.findById(memberId)
}

```

다행히 기존에 구현된 컨트롤러(`ItemController`, `CategoryController` 등)는 성능 최적화를 위해 엔티티 대신 `rq.memberId`를 직접 호출하여 서비스 계층에 넘기고 있어 성능상 문제는 발생하지 않고 있었습니다.

## 2. 문제 인식: 숨겨진 병목과 깨진 유리창 

당장 쓰이지 않는 데드 코드(Dead Code)였지만, 아키텍처를 점검하며 이 코드가 **미래에 심각한 성능 저하를 일으킬 '시한폭탄'**이라는 것을 깨달았습니다.

1. **코틀린 커스텀 Getter의 함정:** `val member`는 한 번 캐싱되는 일반 변수가 아니라 호출할 때마다 `get()` 블록을 재실행합니다. 만약 향후 개발자가 로직 내에서 `rq.member`를 2~3번 참조한다면, 동일한 회원을 찾는 SELECT 쿼리가 2~3번 중복 발생하게 됩니다.
2. **컨벤션의 파편화 위험:** 우리 팀은 "컨트롤러에서는 Entity를 직접 다루지 않는다"는 암묵적인 룰을 잘 지키고 있었지만, `rq.member`라는 손쉬운 탈출구가 열려있으면 언제든 이 아키텍처 룰이 깨질 위험이 존재했습니다.

## 3. 해결 방안: 선제적 방어와 코드를 통한 규칙 강제

문서나 말로 "이건 쓰지 마세요"라고 규칙을 정하는 것보다, **아예 코드로 잘못된 접근을 원천 차단하는 것(Defensive Programming)**이 최고의 설계라고 판단했습니다.

* **`Rq.member` 프로퍼티 완전 삭제:** DB 조회를 유발하는 코드를 삭제하여 잠재적 N+1 문제를 원천 차단했습니다.
* **대체재 확립 및 가이드:** * 식별자가 필요할 때: 기존처럼 `rq.memberId` 활용.
* 부가 정보(이메일, 아이디)가 필요할 때: DB를 찌르지 않고 SecurityContext(메모리)에 이미 로드된 객체를 반환하는 `rq.requireActor()`(UserDto 반환)를 활용하도록 팀 내 가이드를 전파했습니다.



## 4. 결과 및 배운 점 (Result & Learnings)

* **사전 장애 예방 (Proactive Optimization):** 장애가 터진 후 고치는 것이 아니라, 코드 리뷰와 아키텍처 점검을 통해 시스템의 취약점을 미리 발견하고 방어하는 주도적인 리팩토링 경험을 쌓았습니다.
* **제약(Constraint)을 통한 좋은 설계 유도:** 개발자에게 모든 옵션을 열어두는 것보다, 불필요하거나 위험한 API 접근을 막아 자연스럽게 올바른 아키텍처(DTO/ID 기반 통신)를 따르도록 유도하는 것이 진정한 시스템 설계라는 것을 배웠습니다.
